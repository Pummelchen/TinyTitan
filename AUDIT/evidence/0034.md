# AUD-0034 — name the two catalog row shapes and refuse the normalized one

Commit: (see `git log --grep 'audit(0034)'`)

## Root cause

`catalogRows` accepted any array and validated each entry as a *catalog row*
(`quant`, `thinking`). Its own output is a *normalized row* (`levels`, no `quant`),
so a second pass failed every row's `quant` check and — after AUD-0025 — reported
each as `quant is not a number`, returning nothing. The caller-visible result of
`generateBlock(catalogRows(rows))` was therefore an **empty route** that read
exactly like a catalog with no installs. Nothing named the two shapes, and the
silent emptiness had already hollowed one parity test (fixed in AUD-0031).

Measured without the new check:

```
second pass rows: 0
block model line: # 0 served model(s); settings.yaml is hot-reloaded.
```

## Fix

`plugins/dsh-tinytitan/src/generate.js`:

- `catalogRows`'s contract now names both shapes:
  - **catalog row** — what `TinyTitanServer --catalog`, the folder scan and the
    harness listing produce: `{id, name, path, backend, quant, family?, engines?,
    thinking?, size_gb?}`;
  - **normalized row** — what `catalogRows` returns: `{id, name, path, backend,
    family, engines, levels}`.
- `CatalogRowShapeError` (exported, `name` set, and re-exported from
  `src/index.js` beside `catalogRows`) is thrown for the first entry that is
  already normalized. Detection is precise: an object carrying a `levels` array
  and neither `quant` nor `thinking`. It is thrown *outside* the row `try`, so it
  can never be mistaken for a malformed install and skipped — a mixed list fails
  the whole call rather than silently keeping half the rows.
- `generateBlock`'s JSDoc says its argument is the raw `models` array and points
  at the error for anything else.

## Tests

`plugins/dsh-tinytitan/test/generate.test.js` —
`a row that is already normalized is refused, not silently dropped`: both
`catalogRows(rows)` and `generateBlock(rows)` throw a `CatalogRowShapeError` with
`row 1` in the message, a mixed raw+normalized list throws, and a raw list still
produces the two-model block. **RED before**: `Missing expected exception.` (and
the measured 0-row/empty-block output above). The first RED run failed at module
load because the test imports the not-yet-existing class, so the behaviour was
re-measured by removing only the shape check from the finished module.

`plugins/dsh-tinytitan/test/catalog-scan.test.js` — two changes that **strengthen**
the AUD-0031 parity coverage, which is otherwise untouched:

- the measured server rows moved into `measuredServerRows({ gguf, nvfp4, qwen })`,
  used by the Inkling test (same assertions, same values);
- new `a divergent raw row fails the block parity assertion`: a changed display
  name and a changed effort ladder each make `generateBlock` differ, proving the
  block comparison has teeth beyond row count and ids.

The repaired 0031 parity test itself was not edited.

## Residual risk

- The shape check keys on `levels` plus the absence of `quant`/`thinking`. A
  future raw catalog that added a `levels` field and dropped `quant` would be
  reported as a shape error rather than as a malformed row; that is a louder
  failure than the silent one it replaces.
- `catalogRows` remains non-idempotent by design (it refuses instead of passing
  rows through). A caller that wants to normalize once and reuse should keep the
  result and call `buildBlock`-style consumers, not `generateBlock`; the plugin's
  internal callers always pass raw rows.
- `CatalogRowShapeError` is exported from the plugin entry point. It is the first
  error class in that surface; if the surface is meant to stay value-only, it can
  be dropped and callers can match on `error.name`.
