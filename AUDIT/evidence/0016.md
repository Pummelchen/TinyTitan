# Audit 0016 — short `pread` during tail repair truncates unread bytes

**Host / base:** as 0010. Base commit for this task: `ec4222cd`.

## Root cause (confirmed)

`dropDanglingTail` walked the file backwards in 64 KiB chunks:

```swift
let read = pread(descriptor, &buffer, Int(size), offset)
guard read >= 0 else { throw ... }
if let index = buffer[0..<Int(read)].lastIndex(of: 0x0A) { keep = offset + index + 1; break }
end = offset
```

`pread` may return fewer bytes than requested. The scan searched only the prefix it got
and then moved `end` to the chunk's start, stepping over the unread suffix — which is
the *end of the file*, where the last newline and the torn suffix are. `keep` could then
stay at an earlier chunk boundary (or 0) and `ftruncate` removed complete records. A
negative `EINTR` was treated as a hard read failure, and a zero return was accepted as a
read of nothing, which drove the same truncation.

## Fix

`FileJournal+Opening.swift` gains `readExactly(_:into:count:offset:url:using:)`: it reads
the requested range in pieces, retrying `EINTR`, refusing a zero return while `fstat`
says the bytes exist, refusing a return larger than the remaining range, and only
returning once the whole chunk is in the buffer. `dropDanglingTail` searches the chunk
only after that, and `ftruncate` runs only after a newline has been proven (or the file
is genuinely all torn bytes). A failure leaves the file at its original length. The
scan and the truncate still use the same descriptor, under the workspace lock, so no
other opener can separate them.

## Failing-before / passing-after

New suite `tests/ContinuityCore/JournalTailRepairTests.swift`, 9 tests. The short-read
fixture is 64 KiB of a single unterminated record plus `b\n` plus a four-byte torn
suffix; the last newline is 65 531 bytes into the final 64 KiB chunk, and the injected
first read returns 100 bytes from the start of that chunk.

Failing-before run (original one-`pread` loop, seam retained):

```
swift test --no-parallel --filter JournalTailRepairTests
  aShortReadCannotSkipTheLastNewline ............. failed (after != valid; file truncated)
  anInterruptedReadIsRetriedAndTheNewlineStillFound failed (readFailed: Interrupted system call)

  Test run with 9 tests in 1 suite failed after 0.011 seconds with 6 issues.   EXIT:1
```

The short-read failure is the data loss: a complete record larger than one chunk was
cut to nothing. Byte-identical valid tails are asserted by every passing case (exact
64 KiB with the newline last, empty file, multi-chunk history).

After the fix: `Test run with 9 tests in 1 suite passed after 0.010 seconds.` EXIT 0.
`swift test --no-parallel --filter Journal`: 88 tests in 13 suites passed, EXIT 0.

## Residual risk

- External modification of the file between `fstat` and the scan is now reported as a
  read failure (zero/EOF) and leaves the file untouched rather than guessing. The
  workspace lock excludes other `FileJournal` writers, not an arbitrary process; that is
  the 0015 trust model.
- A file whose only newline is more than 64 KiB from a chunk's start is scanned in a
  second chunk; that is unchanged and covered by the multi-chunk test.
