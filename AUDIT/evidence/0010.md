# Audit 0010 — checkpoint replacement ignores durability failures

**Host:** macOS 27.2.1 arm64, 24 GB, Xcode 27.2 / Swift 6.4.2 (swiftlang-6.4.2.1.9).
**Base:** 53ac8466 (detached HEAD of `audit/2026-11-26`), worktree `.agent-worktrees/journal`.

## Root cause (confirmed against the code)

`sources/ContinuityCore/Persistence/Journal.swift:359` discarded the fallback `fsync`
result (`if fcntl(handle, F_FULLFSYNC) == -1 { _ = fsync(handle) }`) and never checked
the strong barrier either. `Journal.swift:367-372` ignored a failed directory open and
a failed directory `fsync`, then returned `.success(())`. A replacement whose bytes
never reached the platter was therefore renamed over the only durable copy; a rename
whose directory entry was not durable was reported as a durable checkpoint.

## Fix

- `sources/ContinuityCore/Persistence/JournalFileSystem.swift` (new): the blocking
  syscalls behind one `Sendable` seam. Production is `SystemJournalFileSystem`, which
  makes the same calls as before and captures `errno` on the line that set it; the tests
  inject a failing implementation. Answers are `>= 0` or `-errno`.
- `sources/ContinuityCore/Persistence/Journal+Rewriting.swift` (new): `writeCheckpoint`
  now checks the strong barrier, checks the fallback, refuses the rename when both fail
  (temp closed and unlinked, original untouched), and answers a three-state
  `CheckpointOutcome` (`.committed`, `.committedWithUncertainDurability(error)`,
  `.failed(error)`). The descriptor is reopened on the new inode for both committed
  states; the uncertainty is then thrown, never rolled back or silently accepted.
- `Journal.swift` / `FileJournal+Opening.swift` / `Journal+Reading.swift`: reads and
  writes go through the seam; the public initialiser is unchanged and delegates to the
  internal seam initialiser.

No public API was removed or renamed. `JournalError` gained `.damagedReplay`,
`.wrongOwner`, `.insecurePermissions` (used by 0014/0015); `FileJournal` gained
`durabilityFailure`, `replayDamage`, `discardDamagedRecords()` (0013/0014).

## Residual risk

- A directory `fsync` that is unsupported rather than transient (e.g. a foreign
  filesystem) now makes every compaction report uncertain durability; the checkpoint is
  still installed and the journal stays usable. This is a deliberate fail-safe choice,
  and the error names the directory.
- A multi-process writer is still excluded by the sidecar flock only; the seam does not
  change that.
