# Audit 0050 — two session-log writes still swallow durability failures

**Host / base:** as 0047. Base commit for this task: `2813451a`.

## Root cause (confirmed)

`ContinuityEngine.remember(sessionID:)` and `assembleContext` wrapped the session-log
record in `_ = try?` (`ContinuityEngine.swift:274,380`). The failure was discarded, so a
session event the log never took left the engine reporting that its file matched its
state. The throw source is `SessionLog.requireSession` (an unknown or pruned session);
the journal append failure inside the observer already reaches `journalFailure`, but the
event's own record failure did not.

## Policy (chosen and documented in the code)

**Best-effort, with a visible degraded-state record.** Both calls write *provenance*
records: in `remember` the fact is already written and durable when the event is
attempted, and in `assembleContext` the snapshot has been assembled and is about to be
returned. Failing the caller would report an operation that succeeded as one that did
not — the opposite of the durability policy elsewhere in this file. The event is still
part of the log, though, so the failure is not dropped: it goes to `journalFailed`'s
channel (`journalWriteFailed`), which is the engine's statement that the file no longer
matches what it holds, and which the memory service already logs once per workspace and
uses to stop claiming durability. The message is `String(describing: error)` — an
"unknown session <uuid>"-shaped description, never the record's value.

No new channel, no new public API.

- `aSessionThatVanishesDoesNotUndoTheFact` — the same shape through the context path.

## Self-audit

- The do/catch records the error instead of swallowing it; there is no remaining `try?`
  in `ContinuityEngine.swift` (grep confirms zero).
- The held-write interleaving is a semaphore the seam signals from the write itself, not
  a sleep; the prune is admitted because the engine is provably suspended in the
  observer.
- Normal cancellation is not involved: neither session-log call can throw
  `CancellationError`, and the journal's cancellation handling is unchanged.
- The failure text is the error's description; no memory value, prompt, or record body
  is included (asserted in the first test).

## File-length split

Adding the reporting took `ContinuityEngine.swift` from 489 to 510 lines, over the
500-line rule, so `assembleContext` moved to `ContinuityEngine+Context.swift` (67 lines)
as pure code motion. No signature changed; `docs/repository-layout.md` records it.

## Residual risk

- `journalFailure` is sticky and its ordinary description says the *file* does not match
  the engine, which is true here, but it does not distinguish "a provenance event was
  lost" from "a fact did not persist". A future dedicated channel could; the memory
  service's degraded log is the current operator-facing report.
- The `remember` failure is only reachable when a session is pruned concurrently with
  that await; the test constructs exactly that, and the call is the same two-line shape
  as the context one.
