# AUD-0044 — GGUF metadata conformance: keys, BOOL and nested arrays

Commit: `audit(0044): …` (see `git log --grep 'audit(0044)'`)

Baseline: detached `522bac35` (after AUD-0043).

## Defects proved before the fix

Three parser gaps against the GGUF v2/v3 contract:

1. **BOOL.** `value(type: 7)` returned `.boolean(byte != 0)`, so 2 and 255
   parsed as `true`. The spec defines the value as one byte where 0 is false,
   1 is true, and "anything else is invalid".
2. **Metadata keys.** Only the 65 535-byte length was checked. The spec requires
   a valid ASCII string with dot-separated `lower_snake_case` segments; keys
   with uppercase, spaces, hyphens, empty segments or non-ASCII bytes were
   accepted and inserted into `metadata`.
3. **Nested arrays.** The reader refused an element type of 9 but the policy was
   only in a code comment; an empty nested array had already been shown in
   AUD-0027 to reach the element-type check. The subset needs stating and
   pinning for both empty and non-empty arrays.

## Fix

`sources/TinyTitanFormat/GGUFHeaderV3.swift`

- `validateMetadataKey` (called for every key before the duplicate check):
  length ≤ 65 535 (same message as before), every byte ASCII, every
  dot-separated segment non-empty and made of `a-z`, `0-9`, `_`. Numeric
  segments are allowed because the spec defines
  `general.base_model.{id}.name`; uppercase, space, hyphen, non-ASCII and empty
  segments are typed `.invalid`.
- `value(type: 7)` reads the byte and refuses anything above 1:
  `"boolean value \(byte) is not 0 or 1"`.
- The type doc now states the intentional one-level array subset explicitly:
  nested arrays are refused as `.invalid("nested array")`, never flattened or
  dropped, because this reader keeps a scalar/flat-array value and no model in
  this tree uses nesting. Supporting nesting would need a recursive value type
  and is not silently partial.

Valid documents are unchanged: the standard keys (including
`general.base_model.0.name`), and BOOL 0/1, parse exactly as before; the
existing v2/v3, tokenizer-array and budget tests still pass.

## Residual risk

- A valid but non-conforming writer that puts uppercase or a hyphen in a key
  would now be refused. The standard and community keys in this tree's
  converters are all `[a-z0-9_]` segments (`general.*`, `inkling2.*`,
  `tokenizer.*`, `split.*`), so no supported model is affected; the spec calls
  such keys invalid.
- Tensor names are not held to the key rule (the spec gives them only a
  64-byte limit and the planner keys on them verbatim); they remain bounded by
  the header and string budgets from AUD-0027.
- Nested arrays remain unsupported by decision; a future model that needs them
  requires a qualified `Value` case and a recursive budget, not a relaxation of
  this check.

## New findings

None beyond the decision recorded above (nested arrays are an intentional,
documented subset).
