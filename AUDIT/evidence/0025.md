# AUD-0025 — malformed catalog rows are reported, not silently dropped

Commit: (see `git log --grep 'audit(0025)'`)

## Root cause

`plugins/dsh-tinytitan/src/generate.js`'s `catalogRows` wrapped each row in
`try { … } catch { continue; }`. Every validation failure — and every programming
error inside the same block — made the model vanish from the picker with nothing
printed, while the mirrored shell parser in `tools/tinytitan_models.sh` prints
`catalog: skipping <id> (<reason>)` to stderr. A broken install was therefore
invisible to the operator on the plugin path, and an unexpected exception (a
throwing getter, a value that cannot be stringified) was indistinguishable from a
malformed row.

## Fix

- `CatalogRowError` — the module's own typed refusal. `catalogRows` catches only
  this class; anything else is rethrown, so a defect surfaces with its stack.
- Every refusal carries a fixed, field-named reason (`the backend is not gpu or
  cpu`, `quant is not a number`, `the id is not a plain model id`, …) and the row
  index; `rowIdentity()` adds `(id <id>)` only when the id already satisfies the
  plain-token grammar, so no other catalog text — a name, a path, a credential, a
  newline — can reach the log.
- `catalogRows(models, { log })`; `generateBlock` and `collectRoute` pass their
  logger through. The diagnostic is
  `dsh-tinytitan: skipping catalog row <n> (id <id>): <reason>`.
- `collectRoute` takes an optional `diagnostics` Set (created once per
  `routeRefresher` and shared by boot and the `models/` watcher): an exact repeat
  of a diagnostic is dropped, the first failure and any changed one still print.
  Folder-scan skips use the same budget.
- All-invalid catalogs: every row is reported, then the existing
  `the catalog describes no servable install under <dir>` failure stands, and the
  settings file is not touched.

## Residual risk

- Severity stays S2: the effect of the pre-fix behaviour was a missing model in the
  picker, not a wrong model or a privilege change.
- The dedupe key is the exact message, so a row whose index shifts because an
  install was added prints again — correct, but an operator renaming installs
  repeatedly will see the line again.
- Diagnostics go to the harness logger (`ctx.logger.info` or `console.log` by
  default), which on a healthy boot the harness does not surface; the sink is the
  harness's, not this plugin's, and that is unchanged.
