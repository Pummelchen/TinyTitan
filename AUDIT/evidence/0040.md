# AUD-0040 — checked resident string-table offset

Commit: `audit(0040): …` (see `git log --grep 'audit(0040)'`)

Baseline: detached `7ee1e051` (after AUD-0039).

## Defect proved statically

`Inkling2GGUFPlanner.planResident` built the resident string table and stored
each tensor name's offset with an unchecked narrowing:

```swift
offsets.append(UInt32(stringTable.count))
```

`UInt32(_:)` traps when the `Int` is outside `0...UInt32.max`. The same line
existed in `Inkling2CheckpointPlanner.planResident` (sibling defect, fixed
here too).

The full-path fixture is not constructible in a test: reaching `2^32` bytes of
tensor names needs either 4 GiB of header (the parser refuses >128 MiB) or 4 GiB
of checkpoint index names (the loader caps the index at
`IndexLoader.maximumIndexBytes` = 64 MiB). The bound that makes it unreachable
is now explicit in the code comment, and the conversion is checked anyway so a
future increase of either cap cannot reintroduce the trap.

**RED note:** the pre-fix expression is inline in a private planning function
and there is no allocation-free way to drive it to `2^32`; the failing-before
proof is the static type fact above (Swift's `UInt32(Int)` traps out of range).
The committed boundary test pins the new checked conversion at the boundary.

## Fix

`sources/TinyTitanRepack/Core/Planning/Inkling2GGUFPlanner.swift`

```swift
static func stringTableOffset(
    _ count: Int, field: String = "resident string table"
) throws -> UInt32 {
    guard count >= 0, let offset = UInt32(exactly: count) else {
        throw RepackError.configurationInvalid(
            detail: "\(field) offset \(count) exceeds UInt32")
    }
    return offset
}
```

Both planners use it. The checkpoint planner's copy is called the sibling
defect audit for this class: same expression, same unavailable bound argument.

## Tests added

`tests/TinyTitanRepack/Core/Planning/Inkling2GGUFPlannerTests.swift`:

- `stringTableOffset(0) == 0`;
- `stringTableOffset(Int(UInt32.max)) == UInt32.max` (the largest representable
  offset);
- `Int(UInt32.max) + 1` and `-1` throw `RepackError`.

No multi-gigabyte allocation; the helper is the exact seam the planners use.

## Residual risk

- The check is unreachable for accepted inputs today; it is a guard against a
  future cap increase, not a behaviour change for any valid install.
- A valid install's offsets are unchanged (the helper returns the same value
  for every in-range count).

None beyond the sibling copy in the checkpoint planner, which is fixed in this
commit.
