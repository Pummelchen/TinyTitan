# Audit 0052 — compatibility reads still drop journal damage silently

**Host / base:** as 0047. Base commit for this task: `821e7c86`.

## Root cause (confirmed)

`FileJournal.read(contentsOf:)` returned only the records that decoded, with no channel
for the complete lines that did not; `MemoryProjectFile.load` — the read behind every
`tinytitan-memory` command — used it, so a damaged project was presented as a whole one.
`ContinuityDemo.inspect` had the same shape.

## Caller audit and chosen contracts

| Caller | Before | Now |
|---|---|---|
| `FileJournal.read(contentsOf:)` | lossy, undocumented | **documented lossy compatibility read**: same records, no damage channel; its doc says a caller that decides anything from the file must use `readDetailed` |
| `MemoryProjectFile.load` | lossy | `readDetailed`; the loaded value carries `damagedRecordLines` |
| `MemoryProjectFile.discover` | `try? load` (unchanged) | still lists a damaged file, now with its damage |
| `tinytitan-memory` `list`/`show`/`delete`/`forget` | no warning | stderr warning naming the workspace, the count and the lines; stdout and exit status unchanged |
| `tinytitan-memory projects` | no warning | same warning per damaged file, on stderr after the table |
| `ContinuityDemo.inspect` | lossy | `readDetailed`; prints a note with the rejected line numbers |
| tests | — | read bytes they wrote; no change |

No record contents are printed: only counts, line numbers and the workspace name.

## Implementation

- `Journal+Reading.swift`: the lossy contract is written down on `read(contentsOf:)`.
- `MemoryProjectFile`: `load` uses `FileJournal.readDetailed`; new public
  `damagedRecordLines: [Int]` (empty when clean). `Fact` and the rest are unchanged.
- `TinyTitanMemoryTool/main.swift`: `warn`/`warnIfDamaged` write to stderr; `resolve`
  warns once for the file a command is about to use, and `projects` warns for each file
  after the table.
- `ContinuityDemo`: `inspect` uses `readDetailed` and prints the note.

## Self-audit

- No caller silently treats damage as empty any more: either it uses `readDetailed`
  (`MemoryProjectFile`, `ContinuityDemo`) or it is the documented lossy read used by
  tests that assert bytes.
- The tool keeps its compatibility: stdout format and exit codes are unchanged; the new
  line is stderr, and it is a warning rather than an error because the readable facts are
  real.
- No record contents or values are logged (only workspace, count, line numbers).
- `discover` still swallows an unreadable file (`try? load`) — that is a different case
  (the file cannot be read at all, not one line) and is outside this task; recorded as a
  residual.

## Residual risk

- `MemoryProjectFile.discover` still drops a file it cannot open at all, with no
  diagnostic. It is the listing path, so such a project is invisible rather than shown
  broken; a follow-up could collect the failure reasons.
- `damagedRecordLines` is 1-based over *lines*, including blank lines, matching what an
  editor shows. A file with CRLF line endings would not decode as the journal expects
  and would be reported as damage on every line — the format has always been
  newline-only.
