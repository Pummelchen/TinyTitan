## 1. Reachability — what was traced

### Offsets

- Definition/contract: `sources/TinyTitanKernelsC/expert_io.c:40-60` (before),
  `include/tinytitan_expert_io.h:38-83`.
- The Swift wrapper is `sources/TinyTitan/Infrastructure/Streaming/ParallelExpertReader.swift`
  (three identical copies under `sources/Engines/DenseGPU` and
  `sources/Engines/Ornith35B4Bit`), constructed by
  `PreadExpertStreamer.swift:381,389,397`.
- Product call sites and their geometry:
  - `PreadExpertStreamer+IO.swift:80,158,180,215,221,228` — offsets come from
    `fileOffset(plan:index:)` (`+IO.swift:309-332`), which proves
    `regionOffset + payload <= layout.streamSize` with overflow reporting and
    returns `layout.streamOffset + regionOffset`; the streamer's open check
    (`PreadExpertStreamer.swift:264-279`) proves `streamOffset + streamSize`
    does not wrap and the file is at least that long. So every offset and every
    full-stride/phase range in the product path is inside the verified file and
    representable as `off_t`.
  - `PreadExpertStreamer+CompressedLoad.swift:45,104,108` — `streamOffset +
    frame.offset`, where a compressed layer's `streamSize` is
    `ExpertBlobIndex.maximumEnd(entries)` (`Model+LayerStreamers.swift:213-226`)
    and the open-time check bounds it against the file, so the sum is safe.
  - `fetch(experts:into:)` (`expert_io.c:287`), the only path that computes
    `expert_id * expert_stride`, is used by product code nowhere: only
    `tests/TinyTitan/Infrastructure/Streaming/ParallelExpertReaderTests.swift`.
- Conclusion: the *product* path never presented an unrepresentable offset, but
  the C entry point accepted one, the header stated no bound, and the Swift
  wrapper exposes raw `[UInt64]` offsets. The failure was the typed-error
  contract: an offset above `OFF_MAX` was cast to a negative `off_t` and
  `pread` answered `EINVAL`, not `EOVERFLOW`.

**Pre-fix proof (subprocess).** `fetch_ranges(offset=UINT64_MAX-3, count=8)` on
an 8-byte fixture, compiled against `git show HEAD:.../expert_io.c`:

```
fetch_ranges(offset=18446744073709551612, count=8) -> 22 (EINVAL=22 EOVERFLOW=84)
```

The same harness against the fixed source: `-> 84 (EINVAL=22 EOVERFLOW=84)`.
The id product has the same class of defect: `id=2^32-1, stride=1<<40` wraps
`uint64` before the fix. Static note: on Darwin a *wrap to a small in-file
offset* always needs a count above `INT_MAX` (id < 2^32, so stride > 2^32),
which `pread` rejects with `EINVAL` and no write; that is why the pre-fix id
path is a wrong-error defect on this platform, and a wrong-read/memory defect
on a platform whose `pread` accepts the full `size_t` count.

### Lifecycle

- `tinytitan_expert_reader_destroy` (`expert_io.c:220-239` before) sets
  `shutting_down`, broadcasts `work_ready`, joins workers and frees mutexes and
  condition variables. An active submitter waits on `work_done`; a queued one
  waits on `batch_idle`; neither is woken by that broadcast, so a concurrent
  destroy is a deadlock/use-after-free.
- The only destroy caller is `ParallelExpertReader.deinit`. Every fetch method
  calls through `self.handle`, so Swift retains the receiver for the duration of
  the call, and `deinit` runs only when the last reference is gone — which
  cannot happen while a call is in flight. Concurrent destroy is therefore
  **not** a supported contract; no close-admission path was added.
- Header now states the destroy precondition explicitly, and the wrapper
  documents why ARC satisfies it (`ParallelExpertReader.swift`, "Lifetime"
  section). The paused-worker test pins the queued-batch handshake; a raw C
  caller that destroys while a fetch is active still violates a documented
  precondition (residual risk, unchanged by design).

## 2. Change

`sources/TinyTitanKernelsC/expert_io.c`

- `tinytitan_checked_mul_u64` / `tinytitan_checked_add_u64` (C99, `UINT64_MAX`
  guards) and `tinytitan_offset_fits_off_t` (round-trip through signed `off_t`).
- `tinytitan_validate_read(offset, length)` refuses, with `EOVERFLOW`:
  a length above `INT_MAX` (Darwin's `pread` cap — measured: `pread` returns
  `EINVAL` for 2^31, accepts `INT_MAX`), an offset above `OFF_MAX`, and an end
  (last byte, not one-past-end) above `OFF_MAX`.
- All three public fetch entry points validate every item *before*
  `submit_batch`, so an invalid batch is never published and no byte is read:
  - `fetch`: checked `id * stride`, then the span;
  - `fetch_offsets`: span at `expert_stride`;
  - `fetch_ranges`: `byte_counts[i]` non-zero (existing) and span at that count.

  that hands an offset to `pread`; `read_one_with` is the shared body.

  `tinytitan_expert_reader_testing_set_gate` (pause a worker deterministically).
  The production read still passes `pread`; the gate is `NULL` in every shipping
  run and costs one predictable branch per expert item.

`sources/TinyTitanKernelsC/include/tinytitan_expert_io.h` — documents the offset

## 6. Residual risk and new findings

- **Residual (documented, by design):** a raw C embedder that calls
  `tinytitan_expert_reader_destroy` while a fetch is active or queued still
  deadlocks/frees under a waiter. The header now states the precondition and
  the Swift owner meets it by ARC. Adding close admission would be a contract
  expansion with no in-tree caller.
- **Residual:** the destination capacity is still the caller's contract; the C
  layer cannot see it. A range validated against the file can still overflow a
  too-small destination. The wrapper's doc states it.
- **Darwin note (new finding, not fixed):** `pread` rejects counts above
  `INT_MAX` with `EINVAL` although POSIX allows `SSIZE_MAX`; the reader now
  refuses such a count itself as `EOVERFLOW`, so callers get a typed error.
- **New finding (low, not fixed):**
  `sources/TinyTitan/Infrastructure/Streaming/ParallelExpertReader.swift:164`
  converts a validated `Int` byte count to `UInt32` with `UInt32($0)`, which
  traps above `UInt32.max` instead of throwing. Internal callers pass
  expert-sized counts, so it is not reachable with a supported geometry.
