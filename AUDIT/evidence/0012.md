# Audit 0012 — serialization of append versus compaction

**Host / base:** as 0010. Base commit for this task: `edac08d0`.

## Reachability (reproduced, not merely a candidate)

The task classified this as an investigation candidate. It is reachable through the
public `FileJournal` API and through `ContinuityEngine`, and the reproduced effect is
data loss, so the severity is S0 per the task's instruction to reclassify rather than
open a duplicate.

- `FileJournal.compact` awaits a blocking-queue replacement after taking the caller's
  snapshot. Actor reentrancy admits `append` during that await; the append writes to the
  **old** descriptor, which the compaction then closes and renames over. The record is
  gone.
- `ContinuityEngine.compactJournal` takes `sessionLog.snapshot()` and `memory.snapshot()`
  across two awaits before calling the journal. A write admitted between them is in the
  journal before the replacement starts, and the checkpoint — taken from the earlier
  snapshot — does not contain it.

Reproduction (new suite `tests/ContinuityCore/JournalCompactionTests.swift`, temporary
original-behaviour patch): see below.

## Fix

Two gates, because the windows are in two places:

- `FileJournal` (append side): `awaitRewrite()`/`acquireRewrite()`/`releaseRewrite()`
  over a continuation queue. `append`/batch wait until no compaction, truncation or
  shutdown owns the descriptor; `compact`, `truncate` and `shutDown` take it exclusively
  and release it on every path (`defer`). No lock is held across an `await` beyond the
  continuation queue itself, and no cooperative thread is blocked.
- `ContinuityEngine` (snapshot side): the same gate around *snapshot capture plus
  replacement* in `compactJournal`, and `record(_:)`, both observers and the memory
  mutation observer wait on it before appending. A write that arrives during a
  compaction is applied to RAM (as before) and journaled after the replacement, so it is
  in the surviving file exactly once; a write already in flight changed the stores
  before the snapshot, so a snapshot taken after admission includes it.
- `FileJournal` also advances `descriptorGeneration` on every swap (already in 0010), so
  an in-flight barrier cannot settle the new file's accounting.

## Failing-before / passing-after

New suite: `JournalCompactionTests`, 5 tests:
`anAppendWaitsForACompactionToFinish`, `aRecordWrittenDuringTheReplaceIsNotLost`,
`competingCompactionsSerialise`, `shutdownWaitsForACompactionInFlight`,
`aMemoryWriteDuringCompactionSurvives`.

Interleaving control: the rename is held by a semaphore the injected filesystem signals
(`holdRename`), so the compaction is paused exactly at the commit point; the append is
then requested and, on the fixed code, is observed as a registered waiter
(`rewriteWaiterCount`, internal) — no sleep. Two tests also wait, bounded (1 s), for a
write signal to establish the interleaving on the broken code; the assertion is the
bytes that survive, which is independent of the wait.

## Residual risk

- The engine gate delays journal appends for the duration of a checkpoint write (a
  rename plus two barriers, tens of milliseconds). Appends already in flight are not
  blocked, and their in-memory effect is included in the snapshot because admission is
  taken before the snapshots.
- A caller that drives `FileJournal` directly (no engine, out of tree) is covered by the
  journal gate; the snapshot-staleness window only exists above it, and only the engine
  takes snapshots.
- Waiting appends are not cancellable individually; a cancelled task that is already
  queued runs once the gate opens. The alternative (dropping a queued append) would
  report a write that never happened.
