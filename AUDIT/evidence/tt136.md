# TT-136 — the 35B-MoE and 122B converters keep a source until its output is durable

Commit: `wiki(tt-136): keep converter sources until their output is durable`
(detached worktree, parent `b083cb65`).

## Root cause

`tools/prepare_agentworld.py` unlinked each downloaded checkpoint shard as soon
as `convert_shard` returned:

```python
convert_shard(path, writers, fused, experts_per_layer)
path.unlink()          # before the fix
```

Converted tensors are not durable at that point. `OutputWriter.add` buffers them
in `block` and only `flush` writes a safetensors shard, at
`OUTPUT_SHARD_BYTES` (4 GiB). For a per-expert checkpoint (KAT-Coder-V2.5-Dev)
the routed experts additionally sit in `FusedExperts` until their whole layer
has arrived, which can be many shards later.

A `SIGKILL` before that flush therefore destroyed the converted bytes and left
the source gone. The resume had nothing to convert from: with no output shard
written yet, nothing at all was adoptable, so the whole fetch restarted — 70 GB
on the 35B, 250 GB on the 122B. The same defect the Qwen 3.8 converter had,
fixed there by `2be28436`.

## Fix

`tools/prepare_agentworld.py`

- `release_durable_sources(pending, writers, fused)` is the new ownership rule:
  nothing in `pending` is unlinked while **any** writer still has `bytes > 0`
  (both widths of a `--bits 4 8` pass are separate writers), and a source named
  by `fused.hold()` — one whose experts are still buffered — is kept even after
  the writers flushed. It is called after every conversion and once at
  completion, after every writer's `finish()`.
- `FusedExperts` records the source shard behind every buffered expert
  (`add(..., source=)`) and reports them from `hold()`; `convert_shard` passes
  the shard path. `release` drops a layer's entry — and so its hold — when the
  layer is emitted.
- `download(..., expected=)` returns a source already that long *before* any
  probe or body request. `main` derives every shard's size once (it did this for
  the progress line already) and passes it, so a complete source in `--work`
  costs no network at all; a partial one still resumes from its last byte with
  the chunked range fetches. A short file still goes through the header-derived
  size check (`expected_size`), so the shortcut is a length check, not a name
  check.
- `main` prints what it is resuming before the first shard request
  (`resuming: N checkpoint shard(s) already in <work> (... GB)`).

Disk: the retention adds the sources since the last 4 GiB flush — about 14 GB of
bf16 at the 35B/122B 4-bit ratio, about 8 GB at the 122B 8-bit ratio — to the
peak, instead of the one-shard floor. `tools/prepare_agentworld.py`'s docstring,
`tools/install_models.sh` (both the `convert_qwen35moe` and
`convert_qwen35moe_solo` comments) and `docs/adding-a-model.md` §5b record it.

**The solo path has no separate rule.** `convert_qwen35moe_solo` (122B) runs one
width per pass and ships a fused checkpoint, so `FusedExperts` is empty and the
rule reduces to "the one writer has flushed". It is covered by its own e2e case
(`--bits 4`) rather than a second ownership rule.

**Nothing was adopted, so nothing stale is dropped.** Unlike
`prepare_qwen38.py`, `OutputWriter` here never scans a previous run's output for
adoptable shards; a resume re-converts from `--work`. The qwen38 fix's "drop
stale sources whose output a previous run adopted" therefore has no counterpart:
a source left on disk is still needed, so it is re-read (no fetch) and released
when the new run's output flushes.

Codec bytes, quantization, naming, `OUTPUT_SHARD_BYTES` and the output partition
are unchanged.

## Test isolation

`prefetch_shards` sets `prepare._stopping` in its `finally` — that is how a
shutdown stops the fetchers — and `download` refuses to start a shard while it is
set. The product runs one conversion per process, so it never sees the flag
again; the test process runs several suites. The first version of this harness
left it set, and running the two suites in the other order exposed it:

```
$ cd benchmark && python -m unittest test_agentworld_resume_e2e test_prepare_agentworld
Ran 32 tests … FAILED (errors=2)
CompleteSourceDownloadTests.test_a_complete_source_is_returned_without_a_probe_or_a_fetch
CompleteSourceDownloadTests.test_a_wrong_size_still_goes_through_the_normal_check
InterruptedError: stopped before this shard started
```

Fixed in the harness, never in the guard: `run_in_process` restores the flag it
found, the e2e's `RestoresModuleState` base class clears it in `setUp` and
asserts it is clear in `tearDown` (a case that leaks fails there, which is how
the missing `super().setUp()` in two subclasses was caught),
`PrefetchShutdownTests` — the unit suite's own shutdown path — clears it in
`setUp`/`tearDown`, and both suites now leave the module global as they found
it. Both orders, 32 tests each:

```
$ cd benchmark && python -m unittest test_agentworld_resume_e2e test_prepare_agentworld
Ran 32 tests in 19.422s
OK
$ cd benchmark && python -m unittest test_prepare_agentworld test_agentworld_resume_e2e
Ran 32 tests in 19.344s
OK
```

## Residual risk

- **No output adoption, so a kill *after* a flush still re-fetches the flushed
  shards' sources.** Sources are released at the flush because the alternative is
  staging the whole source, which the disk rule forbids. The fix removes the
  re-fetch for the case that lost everything (a kill before the first flush) and
  for every source converted since the last flush; making the flushed part
  resumable needs output adoption (qwen38's `conversion.json` + shard scan),
  which this converter has never had and which is a separate change.
- **An orphaned shard file can be left in the snapshot directory** if a run is
  killed after a flush and the resume's shard boundaries differ: the resume
  numbers from 1 and overwrites by name, and an unreferenced
  `model-NNNNN.safetensors` from the previous run can survive beside the
  finished `-of-M` generation. The index it writes never names it, so the
  snapshot is valid; it is dead disk. Pre-existing (the same is true without this
  change), and no test covers it.
- **Retention is bounded by a 4 GiB output block**, so peak disk is up by
  ~14 GB (35B/122B 4-bit) or ~8 GB (122B 8-bit). Those are derived from the
  published source:snapshot ratios, not measured on an install: no 35B or 122B
  model is installed here and none was fetched.
- `w.bytes == 0` means the tensors reached a written shard, not that `fsync`
  ran. That matches the sibling fix's semantics and the failure mode (process
  kill, not power loss).

## New findings

1. **`tools/prepare_k2_horizon.py` has the same defect and no resume.**
   `convert_hf` (line ~379) does `local.unlink()` immediately after converting
   into `ShardWriter`, which buffers to `SHARD_LIMIT_BYTES` (1 GB, line ~281). A
   kill before that flush loses the converted shard with its source gone, and the
   run has to be restarted by hand. It also downloads
   `model.safetensors.index.json` twice (two identical `fetch_json` lines,
   ~330). That script is already TT-053's hand-written install path, so this is
   recorded there rather than changed here: no K2 install exists to verify a fix
   against.
2. `tools/prepare_nemotron.py` writes each tensor straight into the install
   (`write_expert`/`write_resident`) before unlinking its shard, so it does not
   share this defect; `prepare_laguna_s21.py`'s `unlink` is of a download
   part-file after concatenation, also unaffected.
3. `FusedExperts.add`'s `if routed is None` branch (a fused source supplying the
   whole expert axis) is unreachable from `convert_shard`, which only calls
   `add` for per-expert names. Harmless, but the `emit_fused` single-stack case
   it feeds is dead code today; left alone because changing it touches the
   quantization path for no behavioural gain.
