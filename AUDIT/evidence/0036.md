# Finding 0036 (S2) — the example fixtures only built in a directory named `TinyTitan`

**Status:** FIXED (committed on the audit branch, detached HEAD)
**Host:** macOS 27.2.1 (26B131), Apple Silicon arm64, Xcode 27.2 (27B52),
Swift 6.4.2 (`swiftlang-6.4.2.1.9 clang-2100.4.1.1`)
**Files changed:** `examples/embedded/Package.swift`,
`examples/plugin/Package.swift`

## 1. The defect, reproduced

Both fixtures declared `.package(path: "../..")` and then referenced the
dependency as `package: "TinyTitan"` in every target's product dependency.
SwiftPM derives a path dependency's identity from the **last component of the
path**, so the reference only resolved when the checkout directory happened to be
named `TinyTitan`.

Reproduced in a scratch `rsync` copy whose directory is `fixture-copy` (Swift
6.4.2, no other change):

```
$ swift build --package-path .../audit-0036/fixture-copy/examples/embedded
error: 'embedded': unknown package 'TinyTitan' in dependencies of target
'EmbeddedDemo'; valid packages are: 'fixture-copy'
(at '.../audit-0036/fixture-copy')
```

Exit 1, before any compilation. This affects `git clone <url> my-dir`, a tarball
extracted under another name, and every `git worktree` — which is why the 0004
and 0005 verification in this audit had to run in a mirror named `TinyTitan`
(`AUDIT/evidence/0004.md` §6).

## 2. Change

The path dependency now carries an explicit name in both fixtures:

```swift
        // `name:` is not decoration. SwiftPM derives a path dependency's
        // identity from the last component of the path, so in a checkout or
        // worktree whose directory is not called `TinyTitan` the dependency
        // would be named after that directory instead, and `package:
        // "TinyTitan"` below would fail to resolve (`unknown package
        // 'TinyTitan' ... valid packages are: '<directory name>'`). Naming it
        // here is what lets the fixture build from any directory.
        .package(name: "TinyTitan", path: "../..")
```

- `examples/embedded/Package.swift:44` and `examples/plugin/Package.swift:40`.
- The product references (`package: "TinyTitan"`) stay as they are: `name:` is
  exactly the alias those references use. No other line changed — the `path:
  "../.."` relative dependency, the tools version (6.4), the targets, the
  products and the 0004 `demoLanguageStandard` / `swiftLanguageModes: [.v6]` are
  untouched. The dependency is still relative, so nothing is pinned to an
  absolute path or a checkout layout (`grep -nE '/Users/|/private/var'` over both
  manifests: no match).

What the declaration means to SwiftPM, from `swift package dump-package` in the
`fixture-copy` tree:

```
"fileSystem" : [ { "identity" : "fixture-copy",
                   "nameForTargetDependencyResolutionOnly" : "TinyTitan",
                   "path" : ".../fixture-copy" } ]
```

The identity is still the directory basename — SwiftPM does not let a manifest
rename a package — but target dependency resolution now uses the explicit name,
which is the reference that was failing.

## 6. Residual risk / notes

- `name:` is a target-resolution alias; the package *identity* is still the
  directory basename. Anything keyed on identity (a `Package.resolved` pin for a
  path dependency, a registry-style identity check) still sees the directory
  name. For path dependencies there is nothing to pin, and `swift package
  resolve` re-resolves on a rename, so nothing breaks — but a future reader
  should not expect the identity to read `tinytitan`.
- The comment added to both manifests is prose, not behaviour; if the fixtures
  ever stop being path dependencies (a released-tag dependency is the documented
  real-consumer form in `examples/embedded/Package.swift:9`), `name:` becomes
  redundant there. It is harmless and still correct if kept.
- `AUDIT/evidence/0004.md` §6 recorded the identity failure as a deviation from
  that task's verification. A one-line cross-reference was added to it in this
  commit so the deviation does not read as still-open.
