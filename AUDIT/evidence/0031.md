# AUD-0031 — mirror the Inkling 2 plugin installs in the no-binary catalog scan

Commit: (see `git log --grep 'audit(0031)'`)

## Root cause

`plugins/dsh-tinytitan/src/catalog-scan.js` mirrored the *generic* install probe
(`sources/TinyTitanServer/Core/ModelCatalog.swift`), not the plugin probe the
server takes for a declared family that is not a `ModelFamily` case
(`ModelCatalog.probePluginInstall`, `sources/TinyTitanServer/Core/ModelCatalog+Plugins.swift`).
Both shipped Inkling 2 installs declare `arch.family = "inkling2"` and
`arch.hiddenActivation = "situ"`, so the scan resolved the family to the
`qwen36` default and rejected the row at `hiddenActivation !== "silu"`.

Measured on this Mac against the pre-fix module, with `models/` holding only the
two Inkling installs:

```
models: 0
skipped: inkling-2-mini_GGUF-Q4 -> hiddenActivation=situ
skipped: inkling-2-mini_NVFP4 -> hiddenActivation=situ
```

while the server lists both:

```
.build/release/TinyTitanServer --catalog --models-dir models
  inkling-2-mini-gguf-q4  Inkling 2 Mini UD-Q4_K_XL (Unsloth)  inkling2  4  gpu  off,low,medium,high,xhigh
  inkling-2-mini-nvfp4    Inkling 2 Mini                         inkling2  4  gpu  off,low,medium,high,xhigh
```

A profile with no built server therefore saw an empty picker while one with the
server saw two models.

## Fix (`src/catalog-scan.js`)

- `PLUGIN_VARIANTS`: one row per TPP/1 variant the repository ships, matched the
  way each plugin's own `probe` matches — **by the install's model id prefix,
  never by directory name**:
  - `inkling-2-mini-gguf` → display name `Inkling 2 Mini UD-Q4_K_XL (Unsloth)`,
    tokenizer supplied by the plugin (the Q4 install has no `tokenizer/` at all);
  - `inkling-2-mini-nvfp4` → display name `Inkling 2 Mini`, tokenizer must be
    `tokenizer/tokenizer.json` (that plugin supplies no hook).
- The plugin path answers with what `probePluginInstall` reads: the manifest's
  own id **verbatim** (no `_N-Bit` suffix), the plugin's `displayName`, the
  plugin's constant width (`weightBits: 4`), family `inkling2`, `gpu`, and
  `off` + the four supported efforts (`low, medium, high, xhigh`).
- `hiddenActivation` is not gated on the plugin path, because the server's plugin
  probe does not gate it either; a `situ` Inkling is exactly what the family's
  kernels implement. The generic path keeps its `silu` check.
- An `inkling2` manifest whose id matches no shipped variant is refused with
  `an Inkling 2 install outside the variants this project ships`: no plugin
  resolves for it, so the server leaves it off the list and guessing an identity
  would offer a model that cannot be served.
- `size_gb`/`sampling` are not added: the block never reads them, and the parity
  assertion is over the generated block (the server's own values are carried in
  the test fixture so the expected rows are the measured ones).

## Tests

`test/catalog-scan.test.js`:

- `a plugin-backed Inkling 2 install scans as the server describes it` (**RED
  before**: both rows skipped) — synthetic manifests for both variants plus a
  qwen install, asserting the exact rows (id/name/family/quant/backend/engines/
  thinking), that `generateBlock` of the scan equals `generateBlock` of the
  measured server rows, and that the block really carries the three ids, the
  plugin display name and the five-level ladder. The first draft of this test
  compared `generateBlock(catalogRows(rows))`, which is the same double-
  normalization trap described below and compared two empty blocks; it now feeds
  raw rows to `generateBlock` and asserts the block's own ids.
- `an Inkling 2 install the shipped plugins do not recognise is refused` (**RED
  before**: accepted as nothing/skipped with the activation reason) — an
  `inkling2` id outside both prefixes produces no model and a reason naming
  Inkling 2.
- `the scan and the server catalog produce the same picker block` — **repaired**:
  it compared `generateBlock(catalogRows(fromFolder))` with
  `generateBlock(catalogRows(fromServer))`, and `generateBlock` already calls
  `catalogRows`, so the second pass saw normalized rows (`levels`, no `quant`) and
  returned no rows: the assertion compared two *empty* blocks and could not fail
  on a divergence. It now compares `generateBlock(rawRows)` and asserts the model
  count in the block equals the scanned count. With the pre-fix scanner it fails
  on `the parity check needs at least one installed model`.

## Residual risk

- `PLUGIN_VARIANTS` is hand-maintained. A third plugin variant (or a rename of a
  plugin's `displayName`/`modelIDPrefix`) diverges from the scan until the table
  and `catalog-scan.test.js` change; the real-install parity test is what catches
  it, and it needs `models/` and a built server to run.
- The Q4 variant's tokenizer rule mirrors the server's `factory.tokenizerFolder !=
  nil`, which is a *closure* test rather than a call: the server itself lists a
  Q4 install whose GGUF header is missing, and the scan now does too. Reported as
  a server-side finding, not changed here.
- `catalogRows` is not idempotent (normalized rows carry `levels`, not
  `thinking`/`quant`, so a second pass drops them). The repaired parity test no
  longer relies on it; `generateBlock`'s own normalizing pass is unchanged.
