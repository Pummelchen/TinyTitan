# Audit 0019 — the loopback trust boundary

## Investigation result: reachable issue confirmed

The documented model (`README.md`, `docs/server-api.md`, `SECURITY.md`) is:
bind `127.0.0.1`, no authentication, the machine is the trust boundary. Source
confirmed the listener (`HTTPServer.swift:125`) and the only admission check
was Host *presence* for HTTP/1.1. Any `Host` -- and any `Origin`/`Referer` --
was accepted.

That is reachable from a browser, not only from a local process: DNS rebinding
makes an attacker-controlled hostname resolve to `127.0.0.1`, the browser then
treats the server as same-origin, and a `fetch` with `Content-Type:
application/json` needs no preflight. The request reaches `/v1/chat/completions`
and `/v1/models/unload`.

Reproduced before the fix (raw loopback sockets, synthetic backend):

    swift test --no-parallel --filter LoopbackTrustTests
    -> Test run with 12 tests in 1 suite failed after 0.017 seconds with 14 issues.

- `Host: evil.example` + valid JSON POST: 200 and the model was invoked
  (3 failing expectations, including `backend.generations == 0`).
- duplicate `Host`: 200, routed.
- `Origin: https://evil.example`: 200, model invoked.
- foreign `Referer`: 200.
- HTTP/1.0 + foreign `Host`: 200.
- cross-site form POST to `/v1/models/unload`: reached the content-type gate
  (415) rather than the trust boundary; the Origin rule now refuses it first.

CORS was already absent: no preflight answer, no `Access-Control-Allow-Origin`.
No allow-all and no bearer credential were added.

## Change

- `sources/TinyTitanServer/Core/LoopbackTrustPolicy.swift` (new): Host must be
  `127.0.0.1`, `localhost`, `::1` (either IPv6 spelling), with an optional valid
  port. HTTP/1.0 may omit Host; HTTP/1.1 still requires it. `Host`, `Origin`
  and `Referer` must not be duplicated; a present `Origin`/`Referer` must be an
  http(s) URL with a loopback host (port not compared, so a local page on
  another loopback port is still inside the machine boundary).
- `HTTPServerHandler+Routes.swift`: the policy runs before routing, on every
  path. Refusals use the surface's error envelope: 403 `untrusted_host` /
  `untrusted_origin` / `untrusted_referer`, 400 `duplicate_host` /
  `duplicate_origin` / `duplicate_referer` / `invalid_host` / `missing_host`.
- `docs/server-api.md` gained a "Trust boundary" section (exact header policy,
  error codes, CORS, residual local-process risk); `SECURITY.md` gained the
  same model in short form and the do-not-proxy instruction.

No documented client breaks: CLI clients send a loopback `Host` and no
`Origin`/`Referer`; the HTTP tests (URLSession and raw pipelining/HEAD) pass
unchanged. The 415 form gate and the absent-content-type unload contract remain
as task 0020 pins them.

## Tests

`tests/TinyTitanServer/LoopbackTrustTests.swift` (new, 13 tests):

- accepted Host forms (`127.0.0.1[:port]`, `localhost`, `LOCALHOST`, `[::1]`,
  no port);
- foreign Host refused before routing, zero generations;
- a refused HEAD gets the 403 status line with no body;
- duplicate Host refused, zero generations;
- foreign Origin refused, zero generations;
- loopback Origin accepted (three forms, three generations);
- foreign Referer refused, loopback Referer accepted;
- preflight (OPTIONS + Origin + Access-Control-Request-*) not answered with
  CORS, not routed;
- HTTP/1.0 without Host still served, HTTP/1.0 with foreign Host refused;
- HTTP/1.1 missing Host still `missing_host`;
- unload: cross-site form refused (403, model not unloaded); same-machine form
  refused by the media-type gate (415, model not unloaded).

Passing after:

    swift test --no-parallel --filter "HTTPServerTests|LoopbackTrustTests|ResponsesAPIHTTPTests|HTTPMediaTypeTests"
    -> Test run with 70 tests in 4 suites passed after 14.132 seconds.

Gates: `swift-format`, `swiftlint` (0.65.1 --strict), `file-length`,
`func-length`, `test-skip`, `test-hollow` all ok.

## Residual risk (accepted, documented)

- Any local process can still call the server and unload the model. That is the
  declared boundary, not a defect; authentication would not change it.
- `Host` is not compared with the socket's local address beyond the name
  allowlist; a loopback name is the whole policy.
- A proxy or tunnel that rewrites `Host` to a loopback name would bypass the
  DNS-rebinding defence. `docs/server-api.md` and `SECURITY.md` say not to
  expose the port that way.
