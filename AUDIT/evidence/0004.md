# Task 0004 — Enforce required Swift settings in standalone example packages

**Status:** DONE (remediation committed on the audit branch)
**Base commit:** `53ac8466eaea4c269eb6d654c927dbbf5359f9d0` (detached HEAD of the
audit branch, worktree `.agent-worktrees/examples`)
**Host:** macOS 27.2.1 (26B131), Apple Silicon arm64, Xcode 27.2 (27B52),
Swift 6.4.2 (`swiftlang-6.4.2.1.9 clang-2100.4.1.1`), SDK MacOSX27.2
**Files changed:** `examples/embedded/Package.swift`, `examples/plugin/Package.swift`

## 1. The defect, verified against the tree

At the base commit, both example manifests carried `// swift-tools-version: 6.4`
and nothing else about the language standard:

- `examples/embedded/Package.swift:15` — `Package(` with no `swiftLanguageModes`,
  one `.executableTarget` with no `swiftSettings`.
- `examples/plugin/Package.swift:11` — same, with `.target` (EchoPlugin) and
  `.executableTarget` (PluginDemo), neither with `swiftSettings`.

No `swiftLanguageModes`, no warnings-as-errors, no upcoming features. The root
package (`Package.swift:19-24`, `Package.swift:567`) declares all of it:
`swiftLanguageModes: [.v6]` plus `tinytitanLanguageStandard`
(`InferIsolatedConformances`, `ImmutableWeakCaptures`,
`MemberImportVisibility`, `.unsafeFlags(["-warnings-as-errors"])`).

### Measured baseline (before the change)

`swift build --package-path examples/embedded -v` and
`swift build --package-path examples/plugin -v`, flags read from the actual
`swiftc` command line of each example target (resolved from the response file
and the `builtin-SwiftDriver` line):

| target | resolved flags |
| --- | --- |
| `EmbeddedDemo` | `-swift-version 6` |
| `EchoPlugin` | `-swift-version 6` |
| `PluginDemo` | `-swift-version 6` |

So the toolchain default from tools version 6.4 is Swift 6 mode already, and
the recorded evidence is *not* "these compile as Swift 5". What was missing is
the part a tools version cannot provide: nothing declared the mode, and
**nothing enforced warnings** — no `-warnings-as-errors`, no upcoming features.
A warning was a log line, and a future edit to the manifest could drop the mode
with no declaration to notice.

## 2. Change

One local settings array per manifest, applied to **every** target, plus the
language mode on the package:

```swift
let demoLanguageStandard: [SwiftSetting] = [
    .enableUpcomingFeature("InferIsolatedConformances"),
    .enableUpcomingFeature("ImmutableWeakCaptures"),
    .enableUpcomingFeature("MemberImportVisibility"),
    .unsafeFlags(["-warnings-as-errors"]),
]
```

- `examples/embedded/Package.swift:24-29` — array; `:45` `swiftSettings:` on
  `EmbeddedDemo`; `:48` `swiftLanguageModes: [.v6]`.
- `examples/plugin/Package.swift:20-25` — array; `:41` `swiftSettings:` on
  `EchoPlugin`; `:49` on `PluginDemo`; `:52` `swiftLanguageModes: [.v6]`.

Tools version is unchanged (6.4). The root manifest is not imported and no path
into the repository is baked in — the array is restated locally so the fixture
stays a self-contained package, which is the reason it exists. Target set,
product dependencies and the package-relative `path: "../.."` dependency are
unchanged.

`-strict-concurrency=complete` is **not** added to the manifests: Swift 6
language mode already implies complete checking, and the negative control below
shows the compiler enforces it. That matches the instruction to verify rather
than add a redundant manifest flag; the redundancy was measured directly on the
compiler, which accepts `-swift-version 6 -strict-concurrency=complete` (exit 0),
so for 0005 the explicit flag is kept (see `AUDIT/evidence/0005.md`).

### Resolved invocation after the change

| target | resolved flags |
| --- | --- |
| `EmbeddedDemo` | `-enable-upcoming-feature InferIsolatedConformances -enable-upcoming-feature ImmutableWeakCaptures -enable-upcoming-feature MemberImportVisibility -warnings-as-errors -swift-version 6` |
| `EchoPlugin` | identical set |
| `PluginDemo` | identical set |

No target escaped the settings (3 of 3 targets; each package has exactly the
targets listed above).

Manifest-level confirmation — `swift package dump-package --package-path
examples/embedded|plugin` (run in the mirror, §6, because the dump needs the
dependency to resolve):

```
EmbeddedDemo  swiftLanguageVersions: ['6']   EmbeddedDemo: 4 settings
PluginDemo    swiftLanguageVersions: ['6']   EchoPlugin:   4 settings
                                             PluginDemo:   4 settings
```

with each target's four settings being
`enableUpcomingFeature InferIsolatedConformances`,
`enableUpcomingFeature ImmutableWeakCaptures`,
`enableUpcomingFeature MemberImportVisibility`,
`unsafeFlags [-warnings-as-errors]`. The mode is *declared*, not inherited from
the tools version: the flags in the table above have no `-Xswiftc` on the build
command, so the manifest is their only possible source.

## 6. Deviation: verification host is a byte-identical mirror, and why

`swift build --package-path examples/embedded` **fails in this worktree before
any change**, at manifest load:

```
error: 'embedded': unknown package 'TinyTitan' in dependencies of target
'EmbeddedDemo'; valid packages are: 'examples'
(at '/Users/andreborchert/Downloads/TinyTitan/.agent-worktrees/examples')
```

SwiftPM derives the identity of a path dependency from the last path component
of the dependency directory, and both fixtures reference
`.product(name: "TinyTitanLib", package: "TinyTitan")`. In a checkout whose
directory is not named `TinyTitan` (this worktree is `…/.agent-worktrees/examples`;
`git clone …/TinyTitan my-tinytitan` behaves the same), the identity is
`examples`/`my-tinytitan`, and the fixture does not resolve. A symlink named
`TinyTitan` does not help — SwiftPM canonicalises the path and still reports
`examples`.

This is a **new finding, not fixed here** (outside this task's scope, reported
below). To obtain real evidence, the whole tree was copied byte-for-byte to
`/private/var/folders/…/opencode/audit-0004-0005/build/TinyTitan`
(`rsync -a --exclude .build --exclude .git --exclude models`), so the fixtures'
`path: "../.."` and `package: "TinyTitan"` resolve exactly as they do in a
normally named checkout. Every command in §3–§5 was run there against the same
manifest bytes that are committed; the manifests themselves were edited in the
worktree and copied over. The worktree's own tree was never built.

Consequence for the reader: the acceptance commands are reproducible on any
checkout of this repository whose directory is named `TinyTitan`, which is what
the fixtures assume today.

## 7. Not run / residual risk

- **Release-configuration builds** (`swift build -c release --package-path
  examples/embedded|plugin`): NOT RUN. They would rebuild the whole root package
  in release (the fixtures have their own `.build`) and the task names the debug
  invocations; the settings under test are configuration-independent, and the
  release path is covered by `tools/build_library.sh` in 0005.
- **`swift test`**: the fixtures have no test targets; nothing to run.
- Residual risk: `.unsafeFlags(["-warnings-as-errors"])` makes each fixture
  report SwiftPM's "contains unsafe build flags" diagnostic when it is *itself*
  consumed as a dependency. That is the root package's existing posture (which
  is why `tools/embedded-dependency-check.sh` exists and why these fixtures are
  leaves), and it does not affect building or running them, which was measured
  above. It does mean an example could not be depended on by a third package —
  none is, and none is meant to be.
- Residual risk: the three upcoming features are adopted because the tree is
  clean under them; the negative controls prove enforcement, but a future
  upstream warning inside a *fixture source file* would now fail the build
  rather than scroll past. That is the intent.

## 8. New findings (reported, not fixed)

   — `package: "TinyTitan"` binds the fixtures to the checkout directory name.

   valid packages are: 'examples'`. Suggested fix (not applied): declare the
   path dependency with an explicit name, `.package(name: "TinyTitan", path:
   "../..")`, or reference the product by the resolved identity.
