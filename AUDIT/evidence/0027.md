# AUD-0027 — bounded GGUF metadata parser and deterministic duplicates

Commit: `audit(0027): …` (see `git log --grep 'audit(0027)'`)

Baseline: detached `fca2e0d5` (audit branch worktree `format`). Source anchors are
from that tree.

## What was proved before the fix

The parser is fed a downloaded GGUF prefix by exactly two callers:

- local: `RemoteStreamingRepacker.readGGUFHeader` — first read **64 MiB**, then
  `want = max(atLeast, want * 2)` on `.needMoreBytes`, bounded only by the file
  size;
- remote: `prepareInkling2GGUF` — first range **16 MiB**, then
  `want = max(UInt64(atLeast), want * 2)`, bounded only by `info.size`.

So the “maximum header” was the source file's size, and a hostile file could
make the installer materialise it in `[UInt8]` before the parse failed. The
parser itself capped `tensorCount`/`keyCount` below 2^20 but had no byte budget,
walked every element of an array even when only its length was kept, and used
unchecked arithmetic in the cursor, the alignment rounding and both callers'
`Int(dataStart)`.

### Runtime reproduction against the pre-fix parser

`git show HEAD:sources/TinyTitanFormat/GGUFHeaderV3.swift` compiled with a small
harness (`swiftc -package-name auditrepro`) and run:

```
$ ./repro duplicate-key
duplicate key accepted: metadata.count=1 a=unsigned(2)      # last write silently wins
$ ./repro duplicate-tensor
duplicate tensor accepted: tensors.count=2 dims=[[4], [8]]  # ambiguous name -> offset
$ ./repro empty-array
empty array of type 13 accepted: numbers([])                # type never validated
$ ./repro alignment
Swift/arm64e-apple-macos.swiftinterface: Fatal error: Not enough bits…
exit=133                                                    # Int(1 << 63) trap
```

The last line is the local caller's old `want = Int(header.dataStart)`: a
metadata `general.alignment = 2^63` (a legal power of two under the old check)
gave `dataStart = 2^63`, which does not fit `Int`. The test
`GGUFHeaderReadTests.refusesAnAbsurdAlignmentInsteadOfTrapping` is exactly this
case and would crash the test process against the old source.

Static confirmation of the other paths:

- old `Cursor.raw`: `position + count` and `bytes.count * 2` unchecked, and the
  `needMoreBytes` hint could exceed any budget;
- old `Cursor.array`: `for _ in 0..<count { value(type:) }` ran even when
  `keep == false`, so a declared count cost one iteration per element present;
- old alignment: `(headerEnd + alignment - 1) / alignment * alignment` with no
  checked add and no upper bound;
- old metadata/tensor loops inserted into a dictionary/array with no duplicate
  check, so `metadata[key]` and the planner's name-keyed lookups chose an
  arbitrary occurrence.

## Fix

`sources/TinyTitanFormat/GGUFHeaderV3.swift`

- **Budgets**, checked before allocation/iteration:
  `maximumHeaderBytes = 128 MiB` (the real Inkling Q4_K_XL header is 12 MB),
  `maximumStringBytes = 64 MiB` aggregate over keys/strings/string elements,
  `maximumArrayElements = 8 MiB` aggregate for arrays that must be walked,
  `maximumMetadataKeyBytes = 65 535` (the GGUF v2/v3 key limit), and the
  existing `< 2^20` count caps named as constants. A read past the header budget
  is `.invalid`; a read only past the *bytes supplied* stays
  `.needMoreBytes(atLeast:)`, so the retry contract survives.
- **No allocation from a declared count**: an array's minimum payload
  (`count × element size`, checked multiply) and the aggregate element budget
  are checked before asking for bytes. A fixed-width array that is not retained
  (count > `maximumKeptArrayCount`) is advanced with `skip`, not materialised;
  the planner still gets exactly `.longArray(count:)`.
- **Element type validated even when empty**: `elementBytes(_:)` accepts exactly
  the scalar types `value(type:)` accepts (0…12 except 9), so an empty array of
  type 13 or a nested array is refused before the loop that would have skipped
  it.
- **Duplicates refused**: a repeated metadata key or tensor name is `.invalid`
  before insertion. GGUF metadata is a key→value map and the reference writer
  emits each key once; a duplicate has no defined resolution, and tensor
  lookups in the planner are by name.
- **Checked arithmetic**: `raw` checks `position + count` and the growth hint;
  the data start uses `addingReportingOverflow` and must not exceed the header
  budget; the caller's `Int(dataStart)` is now guarded by that budget; dimensions
  must be nonzero.
- `nextHeaderReadSize(current:atLeast:maximum:)` is the one growth policy:
  doubles, caps at the budget, returns nil when the hint itself asks for more
  than a header may be.

Callers:

- `RemoteStreamingRepacker+LocalGGUF.swift` — starts at 64 MiB (or the cap),
  uses `nextHeaderReadSize`, rejects a `dataStart` past the file, and takes an
  `initialBytes` parameter (default unchanged) so growth is testable on a tiny
  file.
- `RemoteStreamingRepacker+RemoteInkling2.swift` — range length is
  `min(want, info.size, maximumHeaderBytes)`, growth uses the same helper, and
  the `dataStart > bytes.count` retry must make progress (a short range is an
  error, not an endless loop).

The serialized GGUF format is untouched: the parser only reads, and the existing
`aSmallFileParses` result is unchanged (same metadata, tensors, alignment and
`dataStart`).

## Tests added

`tests/TinyTitan/Infrastructure/ModelIO/GGUFHeaderV3Tests.swift` (16 new; suite
runs 20 with the existing ones, one gated on the real GGUF):

- valid v2 header; duplicate metadata key; duplicate tensor name; empty array of
  invalid type 13; empty nested array; long uint8 array kept as `.longArray`;
  valid string vocabulary walked and kept as `.longArray`; over-budget declared
  array refused immediately; short array payload asks for more; absurd
  alignment (`2^63`); tensor offset that overflows the address space; rank 0/5;
  zero dimension; string length `2^30`; metadata key `65 536` bytes; growth
  policy (double, cap, nil at/beyond the cap); deterministic 2,000-iteration
  fuzz over capped 4 KiB mutations, asserting only `.invalid`/`.needMoreBytes`
  (with `atLeast <= maximumHeaderBytes`) or a parsed `dataStart` within budget.

`tests/TinyTitanRepack/Core/Remote/GGUFHeaderReadTests.swift` (4 tests):

- a valid header returns the exact header bytes through the local caller;
- a header past the first read grows the read (starts at 8 bytes) and still
  returns exactly `dataStart` bytes;
- `general.alignment = 2^63` is a typed error, not the old `Int` trap;
- a truncated file is refused.

No model download or install was used; every fixture is synthetic.

## New findings (not fixed here)

1. **Sibling unchecked multiply in the GGUF planner.**
   `sources/TinyTitanRepack/Core/Planning/Inkling2GGUFPlanner.swift:63`
   (`dimensions.dropFirst().reduce(UInt64(1), *)`) and `:67`
   (`rows * columns * kept.elementBytes`) are unchecked. Header dimensions are
   untrusted and the parser only rejects zero, not oversized, dimensions, so a
   tensor with two `2^63` dimensions traps there after the header parses. This
   is the same defect class as AUD-0028 but in a consumer; it needs its own
   checked-product task (the parser cannot know ggml block sizes).
2. `Inkling2GGUFPlanner.swift:151` uses `UInt32(stringTable.count)` unchecked;
   with the new 128 MiB header budget the aggregate name bytes cannot exceed
   `UInt32`, so it is currently unreachable, but it is an unchecked narrowing.
3. `Cursor.value(type: 7)` (BOOL) accepts any nonzero byte; the GGUF spec says
   only 0/1 are valid. Not tightened here because it would change acceptance of
   existing files for a value the planner does not consume.
4. Metadata key *characters* are not validated (the spec requires printable
   ASCII hierarchical lower_snake_case); only the 65 535-byte length is
   enforced.
5. Nested arrays (type 9) are still refused although the current GGUF spec
   allows them; this is a pre-existing, documented limitation of this reader
   (arrays are kept as numbers or a length). The fix applies it consistently to
   empty arrays too.

## Residual risk

- The 128 MiB header budget is a policy value. No installed GGUF is close (the
  Inkling header is 12 MB), but a conforming file with a header over 128 MiB
  would now be refused by both callers.
- Rejecting duplicate keys/tensors rejects a non-conforming file that an
  overwrite policy would have read. No known GGUF writer emits duplicates; the
  alternative (last-wins) was the silent ambiguity this task asked to remove.
- The real-model GGUFs are not installed in this worktree, so the
  `TINYTITAN_INKLING2_GGUF`-gated tests were **not run**; the valid-path pin is
  the synthetic `aSmallFileParses` plus the unchanged byte layout tests.
- The remote caller's growth is pinned through the shared
  `nextHeaderReadSize` unit tests and static inspection; no new fake-HF
  integration test was added (the existing fake protocol drives full installs,
  which need a model source).
