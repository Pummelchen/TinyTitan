# Audit 0049 — journal truncate is not made durable

**Host / base:** as 0047. Base commit for this task: `4d7463cd`.

## Root cause (static, confirmed by the seam)

`FileJournal.truncate()` (`Journal+Rewriting.swift:179-199`) opened with `O_TRUNC`,
closed that descriptor and reopened the journal — no `fsync`/`F_FULLFSYNC` on the
truncated file. `O_TRUNC` only changes the inode in the page cache: a power cut can
restore the old length while the records appended afterwards (which *are* barriered)
survive, leaving a journal whose beginning is older than its appends.

## Fix

`truncate()` now takes a barrier on the truncated descriptor before closing it, using
the same strong-then-fallback policy as an append and a checkpoint: `fullSync`
(`F_FULLFSYNC`) first, a checked `fsync` as the fallback. `JournalFileSystem.open` with
`O_TRUNC` is where the length change happens; the barrier is on that descriptor, so no
separate open is needed.

After the attempt the actor follows the file that exists: it resets the append
watermark and reopens the append descriptor in every case, because the truncation is
visible whether or not its durability was proved. A failed barrier is thrown as
`writeFailed(url, errno)`. If the reopen fails as well, the barrier failure is the one
thrown (the operation's failure, not the cleanup's), and `descriptor` is left `-1` so an
append reports `EBADF` instead of writing into a reused descriptor number.

## Self-audit

- The barrier is taken while the rewrite gate is held, on a descriptor that is not the
  append descriptor, before it is closed; the lock is on the sidecar and is untouched.
- No fallback that reports success on a failed barrier; no data-loss path added. A
  failed barrier leaves the file empty (the visible state) and says so.
- `pendingRecords` is zero and `lastBarrier`/accounting match the empty file, so a
  following append cannot be considered covered by the failed barrier.

## Residual risk

- The barrier proves the *file*'s metadata; the directory entry is unchanged by a
  truncation, so no directory sync is taken. On a filesystem where `F_FULLFSYNC` is
  unsupported and `fsync` fails too, the truncation is reported uncertain on every
  call — the same policy as the checkpoint barrier.
- A reused descriptor number is still possible in the kernel after the reopen failure;
  the guard is that `descriptor` stays `-1`, so this type never writes through it.
