# AUD-0039 — checked size products in the Inkling 2 GGUF planner

Commit: `audit(0039): …` (see `git log --grep 'audit(0039)'`)

Baseline: detached `0e8afac9` (after AUD-0027/0028). Source anchors are from the
pre-fix file at that commit.

## Defect proved before the fix

`Inkling2GGUFPlanner.bytes(of:kept:tensor:)` computed the row count and the
element count with plain `*`:

```swift
let rows = dimensions.dropFirst().reduce(UInt64(1), *)
...
return rows * columns * kept.elementBytes
```

`dimensions` comes straight from the GGUF tensor table, which is untrusted (the
header parser now bounds its bytes, not the values). A tensor named
`[UInt64.max, 2]` traps in the reduce before the planner can refuse the file.
The same file also had unchecked cursor sums, a `UInt32` dimension narrowing, an
unchecked `perExpert * experts`, and a `roundUp` whose `value + alignment - 1`
traps at `UInt64.max`.

### RED (temporary fixture, run against the unchanged sources)

A throwaway test called `bytes(of: [UInt64.max, 2], kept: F32)` and expected a

## Fix

`sources/TinyTitanRepack/Core/Planning/Inkling2GGUFPlanner.swift`

- `checkedProduct` / `checkedAdd` helpers return `UInt64` or throw
  `RepackError.configurationInvalid` naming the tensor and field.
- `bytes` checks the rows reduce, `rows * columns`, and
  `rows * columns * elementBytes`. The block path still uses
  `SSDAIBlockEncodingV1.payloadBytes`, which already has checked products and a
  typed `TinyTitanFormatError`.
- `plan` refuses `numLayers <= 0` or `numExperts <= 0` before `0..<numLayers`
  and `UInt64(experts)`.
- `planResident`: the resident index size (`tensors * entryBytes`, `+ header`,
  `+ stringTable`) is checked `Int` arithmetic; every tensor's dimensions are
  narrowed with `UInt32(exactly:)` (typed error, not a trap); cursor updates
  and alignment use checked helpers.
- `planLayer`: `perExpert * experts` and every cursor update are checked.
- `roundUp(_:to:field:)` is now throwing: zero alignment and a value that
  cannot be rounded are typed errors, and the division/multiply is bounded by
  the already-checked padded value.
- The checkpoint planner calls the same `roundUp`; its four call sites add
  `try` and a field label (pure signature follow, no logic change).

Every product/sum on the GGUF planner path is now either checked or bounded by
a value already proven to fit. The plan's result for valid geometry is
unchanged, and the shared `roundUp` behaviour for valid inputs is identical.

## Tests added

`tests/TinyTitanRepack/Core/Planning/Inkling2GGUFPlannerTests.swift` (not gated
on a model):

- `[UInt64.max, 2]` F32 → `RepackError` (rows product);
- `[1 << 62, 2]` F32 → `RepackError` (values × element size);
- `[64, UInt64.max, 2]` NVFP4 → `RepackError` (rows product before payload);
- valid counts unchanged: `[64,2]` F32 = 512, `[64,2,3]` = 1536, `[32,4]` Q8_0
  = 136;
- `roundUp`: 0/1/16384 normal results, `UInt64.max` and zero alignment throw;
- the existing gated model tests still call `roundUp` with `try`.

## New finding (not fixed here)

`Inkling2GGUFArch.archInfo` runs before the planner's own arithmetic and still
has the same class of trap:

- `sources/TinyTitanRepack/Core/Format/Inkling2GGUFArch.swift:16,19,20,83` —
  `Int(Double)` from untrusted metadata traps on NaN, infinity or a value
  outside `Int` (`inkling2.block_count = 1e300` is enough).
- `Inkling2GGUFArch.swift:31` — `(passes - 1) * (loopEnd - loopStart)` is an
  unchecked `Int` product from those values, and `:87` has `layer + ...` on the
  same pattern.
- `Inkling2GGUFArch.swift:110` — `1 / Double(p.headDim).squareRoot()` yields
  infinity for `headDim = 0` (no trap, but a non-finite geometry).

These need their own task on the architecture reader; bounding the planner's
products does not make a hostile architecture metadata document safe. The
committed planner tests use valid arch values so they reach the dimension
arithmetic this task owns.

## Residual risk

- The planner's file-size check (`sourceTensor`) still rejects a size past the
  real file, so a product that fits `UInt64` but is huge fails there rather than
  allocating; this task removes the trap, not the need for that check.
- `roundUp` is now throwing; the only external callers were the two planners and
  two tests, updated here.
