# Audit 0013 — asynchronous journal durability failures are swallowed

**Host / base:** as 0010. Base commit for this task: `cab4e1d0`.

## Root cause (confirmed)

`sources/ContinuityCore/Persistence/Journal.swift:140-146` ran the scheduled barrier as
`try? await self.performBarrier()`; the task has no caller, so the failure ceased to
exist. `shutDown` (`:393-400`) is declared `async throws` but wrapped both its flush and
the close in `try?`, so a storage failure produced an apparently clean shutdown with
records unsynced. `ContinuityEngine.shutDown` (`ContinuityEngine.swift:146-150`) also
discarded both failures, and `MemoryService.shutDown` never asked.

## Fix

- `FileJournal.performBarrier` now returns `JournalError?` and records it in
  `public private(set) var durabilityFailure`; a later successful barrier clears it
  (the records are durable at that point, so a sticky warning would lie).
- The scheduled barrier does `_ = await self.performBarrier()` — no `try?`, no catch;
  the outcome exists on the actor before the task completes. `Task.sleep`'s one error
  (cancellation) is handled by `sleepUnlessCancelled` and is not a failure.
- `shutDown` acquires the descriptor, settles any running barrier, retries the flush
  once, closes both descriptors and releases the flock, then throws the original
  failure (`defer` releases the rewrite gate on every path). A second `shutDown` is a
  no-op and does not throw.
- `ContinuityEngine.endSession`/`shutDown` record a failed `flush()`/`journal.shutDown()`
  on `journalFailure` instead of `try?`.
- `MemoryService.shutDown` reads the engine's durability channel for every workspace,
  after closing it and before dropping it, and logs it through the existing
  once-per-workspace `journalFailed(in:)` path.

No public signature changed; `ContinuityEngine.shutDown` stays non-throwing and
`MemoryService.shutDown` stays non-throwing, with the failure on the existing channel
(and the log) rather than an invented return value.

## Residual risk

- `shutDown` retries the flush exactly once. A drive that fails both the running
  barrier and the retry throws the retry's error; the earlier one is overwritten by the
  same category (both `writeFailed`).
- The memory service logs the failure once per workspace; a process that exits without
  calling `shutDown` still loses it (unchanged: nothing to read after the process).
