# Audit 0048 — sub-second timestamps are lost on journal replay

**Host / base:** as 0047. Base commit for this task: `a355707f`.

## Root cause (reproduced)

The journal's encoder and decoder both used `.iso8601`
(`Journal.swift:122,126`; `Journal+Reading.swift:50`), which formats and parses whole
seconds. A `Date` of `1795701827.784161` came back as `1795701827.0`, so a replayed
record was not the record that was written, and two events inside one second came back
indistinguishable.

## Fix

- `FileJournal.makeEncoder()` encodes `Date` with
  `ISO8601DateFormatter.formatOptions = [.withInternetDateTime, .withFractionalSeconds]`
  in UTC. The on-disk form is `2023-11-14T22:13:20.123Z`: the same ISO 8601 instant as
  before, with the milliseconds `Date` already carries. This is the documented journal
  precision: milliseconds survive, anything below them does not.
- `FileJournal.makeDecoder()` accepts **both** forms: fractional first, then the
  whole-second form every earlier build wrote. An existing install replays unchanged and
  a record written by this build decodes with its timestamp intact.
- The formatters are created per call. `ISO8601DateFormatter` is a reference type
  Foundation does not declare `Sendable`, and an encode runs on the actor while a replay
  of another journal runs on the blocking queue; two formatter constructions per date is
  cheaper than a shared mutable object with a hand-written invariant.
- No schema change; ordering and retention read the same `Date` values, now more precise.

## Failing-before / passing-after

New suite `tests/ContinuityCore/JournalTimestampTests.swift`, 4 tests:

- `aSubSecondTaskRecordRoundTripsExactly` — `.123`/`.987` are in the written bytes and
  the replayed record equals the original.
- `theDocumentedPrecisionIsMilliseconds` — `.123456` writes `.123Z` and replays to
  `.123` (the documented loss).
- `anOldWholeSecondTimestampStillDecodes` — a legacy encoder fixture, pinned to
  `"createdAt":"2023-11-14T22:13:20Z"`, decodes to the same instant.
- `aCheckpointRoundTripsItsTimestamps` — task/session/memory dates in a checkpoint come
  back within a millisecond of the in-memory values.

Failing-before run (both strategies restored to `.iso8601`):

```
swift test --no-parallel --filter JournalTimestampTests
  aSubSecondTaskRecordRoundTripsExactly ...... failed (no .123 in bytes; replayed != original)
  theDocumentedPrecisionIsMilliseconds ....... failed (no .123 in bytes; second precision)
  aCheckpointRoundTripsItsTimestamps ......... failed (5 dates beyond 1 ms)
  Test run with 4 tests in 1 suite failed after 0.051 seconds with 11 issues.   EXIT:1
```

`anOldWholeSecondTimestampStillDecodes` passed before and after (it is the compatibility
guard). After the fix: 4/4 passed; `swift test --no-parallel --filter Journal`: 95 tests
in 15 suites passed, EXIT 0. The comment in `JournalWriteLoopTests` that attributed the
title-only comparison to lost sub-second precision now attributes it to `Date()` being
finer than the journal's milliseconds; the assertion itself is unchanged.

## Self-audit

- Two decoder construction sites exist (`makeDecoder`, used by `replay` and
  `readDetailed`); both now use the same strategy. Encoding is only `makeEncoder`.
- Session retention/ordering compares `Date`s as before; more precision cannot reorder
  two events that were previously distinct. Tests that assert exact equality of a
  *created* `Date()` (sub-millisecond) still compare fields, not whole records — no
  fixture was changed to accommodate the new precision.
- Old records decode; no migration is written or required.

## Residual risk

- Anything below a millisecond is truncated (documented). A caller that needs exact
  `Date` equality must construct the date at millisecond precision.
- Parsing allocates a formatter per date. Replay is a startup operation and the cost was
  not measurable in the journal suites; if a huge journal's replay ever matters, a
  `Sendable` `Date.ISO8601FormatStyle` can replace it without changing the bytes.
