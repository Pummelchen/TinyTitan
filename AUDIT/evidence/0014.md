# Audit 0014 — corrupt complete records are indistinguishable from a torn tail

**Host / base:** as 0010. Base commit for this task: `65f4fb0f`.

## Root cause (confirmed)

`Journal.decodeRecords` (`Journal.swift:273-289` before this task) used `try?` on every
complete line and appended only the decodes that succeeded. A complete line that did not
decode — a bit flip, a file reused after truncation, a record from an incompatible
build — vanished with no diagnostic. The replay then reported success, and the next
compaction replaced the file with a checkpoint built from the surviving records, which
is the only way a replay can turn a damaged file into a permanently damaged one. The
existing test `aTornTailIsDroppedAndTheRestSurvives` shows both shapes in one fixture: a
torn final line (dropped correctly) and a complete unknown record (dropped silently).

## Fix

- `JournalReplayDamage` (line number, byte offset, no contents — a damaged line may
  hold a prompt), `JournalReplay` (records + damage) and
  `JournalError.damagedReplay(URL, lines:)` in `JournalTypes.swift`.
- `Journal+Reading.swift`: `decodeJournal` classifies a complete undecodable line as
  damage and a final unterminated line not at all; blank lines are skipped, not damage.
  `FileJournal.replay` sets `public internal(set) var replayDamage`; `readDetailed` is
  the read-only way to get positions, `read(contentsOf:)` keeps its shape.
- `Journal+Rewriting.swift`: `compact` and `truncate` refuse with `.damagedReplay`
  while `replayDamage` is set, before writing anything. `discardDamagedRecords()` is the
  explicit operator recovery step that clears it; nothing in the package calls it.
- `ContinuityEngine.journalDamage` is computed from the journal (so recovery clears it,
  no stale cache). `ContinuityStore.journalDamage` exposes it;
  `MemoryService.journalFailed` reports it once per workspace as
  `degraded during journal-damage` and makes `isDurable` false — the store in RAM is
  missing records the file still holds.
- Availability is preserved: the good records are replayed and the engine starts.

`tests/TinyTitanMemory/MemoryDamagedJournalTests.swift` (1 test). Fixtures splice whole

## Residual risk

- A complete damaged line is preserved but not recoverable by this code; the operator
  must copy the file and decide. That is the documented recovery policy.
- `read(contentsOf:)` still returns records only, so a tool built on it does not see
  damage; `readDetailed` is the API that does. Existing callers (`MemoryProjectFile`)
  keep their behaviour.
- Damage is only detected by a replay. A process that opens, appends and compacts
  without replaying (not done by the engine) keeps the old behaviour.
