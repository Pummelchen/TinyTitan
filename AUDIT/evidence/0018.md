# Audit 0018 — bound stored response memory by bytes and chain size

## Finding: confirmed, statically and by test

`ResponseStore` capped entries at 256 and accounted nothing else. Each entry
retains `responseJSON`, `inputItems` and `outputItems`; `handleResponses`
flattens the prior conversation into `storedInput = prior + inputItems`, so
every continuation duplicates the whole history. A count cap therefore bounded
the number of entries, not the memory they held.

Pre-fix behaviour was reproduced with a probe that uses only the old API: a
synthetic backend returning 17 MiB of text, one `POST /v1/responses` (default
`store: true`). Against the parent commit:

    swift test --no-parallel --filter PreFixStoreProbe
    -> Test run with 1 test in 1 suite failed after 0.312 seconds with 2 issues.
       Expectation failed: object["store"] as? Bool == false
       Expectation failed: (fetched as? HTTPURLResponse)?.statusCode == 404

The old store kept the 17 MiB entry and told the client `store: true` (the GET
returned 200). The probe was removed after capturing the result; the permanent
test below is the same request.

## Change

`sources/TinyTitanServer/Core/ResponsesAPIStore.swift`:

- `PutOutcome` (`stored`, `rejectedEntryTooLarge`, `rejectedNoCapacity`,
  `rejectedUnmeasurableEntry`) so no caller has to guess.
- `maximumEntryBytes` (default 16 MiB) and `maximumTotalBytes` (default 64 MiB)
  alongside `capacity` (256). A `bytesByID` map plus `retainedBytes` gives O(1)
  delete and replacement accounting.
- Logical size = `responseJSON` + the JSON of every input and output item,
  measured once before the lock, with checked addition
  (`addingReportingOverflow`). An encoding failure refuses the entry instead of
  under-counting it.
- Deterministic order, unchanged: replacement refreshes the id; eviction is
  oldest-first, the new entry is never evicted; a refused put changes nothing
  (entry, order and accounting). `totalRetainedBytes` never exceeds the budget
  for a positive budget.
- `item(withID:)` no longer builds `outputItems + inputItems` per entry; it
  searches output then input, preserving precedence.

`sources/TinyTitanServer/Core/HTTPServerHandler+Responses*.swift`:

- A `store: true` request whose flattened conversation already exceeds
  `maximumEntryBytes` is refused with 400 `stored_response_too_large`
  (`previous_response_id`, or `input` on the first turn) **before generation**.
- `storeResponse` returns whether the entry was stored. Both the
  non-streaming object and the streamed terminal object attempt the store
  before emitting `store`, and report `store: false` when it was refused, so a
  client is never told a response is retrievable when it is not.
- `store: false` is unchanged and never consults the budget.
- `TinyTitanHTTPServer.init` takes an optional `responseStore`, internal
  (package) API only, so the HTTP tests can use small budgets.

`docs/server-api.md` documents the three bounds, eviction, `store: false` on
refusal and the pre-generation 400.

## Eviction/rejection semantics, stated

- Refused put: no state change; the outcome is returned.
- Count or total-byte pressure: oldest entries are evicted until the new entry
  fits; the new entry is never evicted.
- One entry over `maximumEntryBytes` or over `maximumTotalBytes`: rejected,
  reported as `store: false`, and not retrievable (404). Over-budget `input`
  on a continuation: 400 before generation.
- `store: false`: no budget interaction.

## Residual risk

- Bytes are logical JSON sizes; allocator overhead, Swift array capacity and
  shared buffers are not counted, so RSS can exceed the logical 64 MiB. This is
  documented rather than measured as RSS in the suite (allocator caching would
  not return anyway).
- The 256-entry cap still allows 256 tiny entries; the total budget is the
  memory bound.
- A stored entry may be evicted by later responses; that is cache semantics,
  and the `GET` 404 is the documented result. A client holding an old id can
  no longer continue it (`previous_response_id` 404), unchanged from before.
