# AUD-0028 — overflow-safe compressed expert block-count arithmetic

Commit: `audit(0028): …` (see `git log --grep 'audit(0028)'`)

## Defect proved before the fix

`ExpertBlobIndex.blockCount` computed

```swift
Int((phaseBytes + blockBytes - 1) / blockBytes)
```

after a positivity guard only. The addition is unchecked `UInt64` arithmetic, and
`phaseBytes` is the install's `layout.json` `expertStride` (or `stride - down`
for phase 1), which the reader validates only as `> 0` and a multiple of
`SSDAIFormatV1.alignmentBytes` (`SSDAIPackedExpertsLayoutV1.swift:151-153`). A
corrupt or hostile install can therefore name `expertStride = UInt64.max`; the
reader's `compressedLayout` passes it straight to `decodeLayout` →
`blockCount`, which traps with Swift's overflow trap (SIGTRAP), not a typed
error.

The `Int(...)` conversion was the second trap: a 1-byte block size (reachable
from the package API, not from `decodeLayout`, whose exponent floor is 12) would
overflow `Int` for a large phase.

## Fix

`sources/TinyTitanFormat/ExpertBlobIndex.swift`

- `blockCount` returns the exact ceiling as `UInt64`, computed as quotient plus
  a nonzero remainder. That form cannot overflow: a nonzero remainder implies
  `blockBytes > 1`, so `quotient <= UInt64.max / 2` before the increment.
- `decodeLayout` sums the two phases with `addingReportingOverflow`, then
  enforces `1...maximumBlocksPerExpert` and only then converts the (≤ 128)
  result to `Int`. A phase at the integer limit is a typed
  `Failure.badBlockCount(4_503_599_627_370_496)`, not a trap.
  `badBlockCount` now carries `UInt64` so the reported count is not saturated.
- `blockOutputBytes` is private and returns `nil` for an index that is not a
  block of the phase; its `index * blockBytes` and `phaseBytes - start` are
  checked (the old version trapped on a negative index and could underflow).
- `blockDestination` rejects a negative index, checks the tail multiply and the
  `phase0Bytes + tailOffset` add with `addingReportingOverflow`, and still
  returns nil for an index outside the layout.
- The codec layout is untouched: v2/v3 serialize exactly as before (pinned by
  the new byte-for-byte test).

Signature ripple (required by the `Int` → `UInt64` return): the three verbatim
`packedPhaseRanges` copies
(`sources/TinyTitan/Infrastructure/Streaming/PreadExpertStreamer+CompressedLoad.swift`,
`…/Ornith35B4Bit/Streaming/…`, `…/DenseGPU/Streaming/…`) now compare a block
count against `UInt64(pack.count - index)` before converting it; the range
arithmetic is unchanged.

## Tests added

`tests/TinyTitan/Infrastructure/Streaming/ExpertBlobIndexTests.swift` (7 new,
suite `ExpertBlobIndexTests`, 17 tests with the existing ones):

- phase 0, block 0, one byte, exact multiple, one past, 4 MiB at 4 KiB;
- the format maximum: 128 × 1 MiB → 128, one byte more → 129;
- `UInt64.max` at 4096 → 2^52, at 1 → `UInt64.max`, `Int.max` at 4096 →
  `Int.max / 4096 + 1` (the two old traps);
- `decodeLayout` with a 129-block phase → `.badBlockCount(129)`;
- `decodeLayout` with `phase0Bytes = UInt64.max` → `.badBlockCount(2^52)`;
- v3 writer→reader roundtrip, and the serialized bytes compared with the
  documented header + entries layout byte for byte (`TTXI`, v3, exponent,
  reserved, count, little-endian u64/u32 pairs);
- `blockDestination` starts/output sizes for both phases (including the partial
  last block and the out-of-range/negative index `nil`);
- a tail offset that would wrap `phase0Bytes + tailOffset` → `nil`.

No huge allocation: all values are arithmetic; the largest buffer is the
existing 8-expert synthetic index.

## New findings (not fixed here)

1. `ExpertBlobIndex.maximumEnd` (`ExpertBlobIndex.swift`, the `[[Blob]]`
   overload) still computes `frame.offset + UInt64(frame.length)` unchecked. Its
   doc says entries come from `decode`, which already refuses a wrapping end,
   so it is a documented precondition rather than a reachable trap; recorded
   because it is the same unchecked-add shape.
2. `CompressedExpertLayerGeometry.rawBytes`
   (`sources/TinyTitanRepack/Core/Writing/CompressedExpertLayerWriter.swift:39`)
   computes `expertStride * UInt64(expertsPerLayer)` unchecked, and
   `validate()` (`:48-73`) bounds only `expertStride <= Int.max`, not the
   product. The tool path checks the product itself
   (`CompressExpertsTool.swift:194-200`), so this is reachable only through a
   direct library call with absurd geometry; a writer-side checked product or a
   `rawBytes` validation belongs in its own task.
3. `CompressExpertsTool.swift:117` multiplies `rawLayerBytes *
   UInt64(layers.count)` unchecked; each factor is a real on-disk layer size, so
   the product is a plan-level total rather than untrusted geometry. Recorded,
   not changed.

## Residual risk

- The reader's own guard (`expertStride` > 0, page multiple) is still the only
  upper bound besides `decodeLayout`'s 128-block check; the streamer therefore
  rejects a corrupt huge stride at `decodeLayout` instead of trapping anywhere.
  `blockDestination` is total for any `UInt64` phase/bytes pair.
- `maximumBlocksPerExpert = 128` is unchanged, so no valid geometry changes.
- No model install was needed or used; the roundtrip uses the synthetic layer
  already in the suite.
