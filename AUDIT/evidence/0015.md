# Audit 0015 — journal file type, ownership and permissions are not validated

**Host / base:** as 0010. Base commit for this task: `aa68d68e`.

## Root cause (confirmed; investigation candidate resolved)

`O_NOFOLLOW` and the create mode `0600` only govern the final path component and a file
this process creates. They say nothing about a file that already exists:

- `readContents` (`Journal+Reading.swift`) opened `O_RDONLY` and read until EOF: a final
  symlink was followed, a FIFO opened without `O_NONBLOCK` blocked, and a device could
  be read without bound.
- `openForAppend`/`acquireLock` never checked the descriptor they got back, so a FIFO,
  device, directory, foreign-owned file or world-readable journal was accepted.
- The read path had no type check at all; `FileJournal.read` on a FIFO blocked forever
  (reproduced, see below).

The threat model is the operator's store directory, which may be a symlink on purpose.
A blanket path ban would be wrong, and it is not what this does: the journal file's
final component must be one regular file, owned by this user, and (for writing) not
readable by anyone else.

## Fix

`FileJournal+Opening.swift`: `validateRegularFile(descriptor:url:using:checkOwner:checkMode:)`
`fstat`s the descriptor that was actually opened and refuses anything that is not
`S_IFREG`; adding the owner check at the append and lock openers, and the `0o077` mode
check at the append opener. The compaction temp is type-checked only. `openForAppend`,
`acquireLock` and the temp create add `O_NONBLOCK` so a special file cannot block the
open. `readContents` adds `O_NOFOLLOW | O_NONBLOCK`, maps `ELOOP` to `.notAFile`, and
type-checks the descriptor (no owner/mode check: a legacy permissive journal is exactly
what an operator runs the read-only inspector to diagnose; the write path is where it is
refused).

`JournalError` gains `.wrongOwner(URL, uid:)` and `.insecurePermissions(URL, mode:)`; the
latter's description names `chmod 600` as the repair. Nothing chmods, truncates or
deletes a refused file. A same-owner hardlink is **not** refused: the same user can
already write the target, so it is not a privilege boundary, and refusing it would break
an operator's own backup link.

## Failing-before / passing-after

New suite `tests/ContinuityCore/JournalFileTypeTests.swift`, 10 tests. Scratch
directories, real `mkfifo`, real symlinks and real modes; the wrong-owner cases use the
injected `fstat` seam because creating another uid's file needs privileges.

Failing-before run (original openers: no type/owner/mode checks, read follows links):

```

  aDirectoryAtTheJournalPathIsRefusedByTheReadPath .. failed (readFailed, not notAFile)
  aFIFOAtTheJournalPathIsRefusedByTheWritePath ...... failed (FIFO opened for append)
  aPermissiveExistingJournalIsRefusedAndLeftAlone ... failed (0644 journal opened)

  aLockOwnedByAnotherUserIsRefusedAndCreatesNoJournal failed

```

The FIFO read test blocks on the original code instead of failing, so it was run alone
under an external 25 s deadline (the committed code opens with `O_NONBLOCK` and refuses
by type in microseconds):

```
TIMEOUT: the read blocked on the FIFO for 25s (killed)
```

The lock-FIFO test passed even on the original because `flock` refuses a FIFO (with an
error the old code reported as a general open failure); it is kept as a regression test,
not claimed as a fixed defect.

After the fix: `JournalFileTypeTests` 10/10; `JournalSymlinkTests` + `JournalTests`
(including the intentional directory-symlink case) pass; EXIT 0.

## Residual risk

- A hardlink to another file this user owns is accepted by design (same-owner model;
  see above). Hardlinking another user's file is refused by the owner check.
- A permissive legacy journal is refused for writing until `chmod 600`; that is a
  deliberate fail-safe and the error says so.
- `readContents` still reads a regular file until EOF; a same-user process can still
  make that file enormous, which costs memory but crosses no boundary it did not
  already cross.
