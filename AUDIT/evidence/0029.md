# Audit 0029 — zero-progress write loops

**Host / base:** as 0010. Base commit for this task: `718c356d`.

## Root cause (confirmed)

Both `writeFully` loops (`Journal.swift:155-170` instance, `:410-424` checkpoint)
advanced by the return value only:

```swift
let written = write(...)
if written < 0 { ... }
offset += written
```

A `write` that returns 0 with bytes remaining neither throws nor advances, so the loop
never terminates — with the record half-written and the actor stuck. `write` normally
returns 0 only for a zero-length request, which the loops never make, but a seam or a
filesystem is exactly where "normally" stops holding.

## Fix

- One shared `writeFully(_:to:url:using:)` in `Journal.swift`, called by the append path
  and the checkpoint path. Every positive remaining byte count now requires positive
  progress: `written == 0` → `JournalError.writeFailed(url, errno: EIO)`; a return
  larger than the remaining slice is also refused (it would advance the pointer past the
  buffer). `EINTR` is still retried, short positive writes are still continued, and an
  empty buffer still writes nothing.
- `Journal+Rewriting.swift`'s checkpoint helper uses the same function; a zero-progress
  or hard failure unlinks the temp and never renames it.
- Partial append: a failed write sets `tornTail`, and the next `append`/batch cuts the
  file back to its last newline **through the append descriptor** (`dropDanglingTail`)
  under the rewrite gate before writing. Without it the next record fuses with the
  partial line and both decode as neither — the failed append was reported, and the
  successful one would be lost silently. `compact`/`truncate` reset the flag with the
  new file.

## Failing-before / passing-after

New suite `tests/ContinuityCore/JournalWriteLoopTests.swift`, 7 tests. Injected write
plans terminate after the zero (`[.zero, .failure(EPIPE)]`), so the original loop stops
on the injected failure instead of hanging the runner; the assertion is the *number* of
write calls, which distinguishes "stopped at the zero" from "retried it".

Failing-before run (original loop, no torn-tail repair):

```
swift test --no-parallel --filter JournalWriteLoopTests
  aZeroProgressWriteFailsTheAppendInsteadOfSpinning ... failed (code EPIPE not EIO; writes 2 not 1)
  aShortWriteThenAZeroKeepsTheExactPrefixAndRepairsTheTail ... failed
      (code EPIPE; writes 3 not 2; replayed.count 0, wanted 1)
  theCheckpointWriteHasTheSameZeroProgressGuard ... failed (code EPIPE; writes 2 not 1)
  Test run with 7 tests in 1 suite failed after 0.031 seconds with 8 issues.   EXIT:1
```

The `replayed.count == 0` on the short-write test is the fused-line loss: the next record
landed on the torn tail and neither line decoded.

After the fix: `Test run with 7 tests in 1 suite passed after 0.045 seconds.` EXIT 0.
`swift test --no-parallel --filter Journal`: 57 tests in 9 suites passed, EXIT 0.

## Residual risk

- `EIO` is used for a zero-progress write because the kernel did not supply an `errno`;
  the message names the file, not a code the drive chose.
- The repaired prefix is dropped, not archived: the append that wrote it returned an
  error, so no caller was told it was stored. A caller that wants the bytes must read
  them before the next append repairs the file.
